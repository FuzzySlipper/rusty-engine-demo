# Rusty Engine Demo

This repository is the reference downstream consumer of
[Rusty Engine](https://github.com/FuzzySlipper/rusty-engine): a complete, small game — the Doom
E1M1 "Hangar" demo — built the way a new game should be. It shows the structure, seams, and
authoring workflow a downstream repo can copy.

## What this repo demonstrates

- **A downstream `gameplay/` crate.** All game-owned gameplay semantics live in
  `gameplay/` (`loading-bay-gameplay`): combat, vitality, inventory, pickups, enemies,
  encounters, doors, interaction, progression, hazards, projectiles, lifts, players, scheduling,
  save games, and the authored-definition compiler. The product shell
  (`rust/crates/loading-bay-game`) keeps only the fixed-tick loop, hosts, persistence glue, and
  the Studio adapter — it consumes the gameplay crate as a workspace dependency.
- **Engine capabilities adopted by name, never forked.** The game consumes the Engine only
  through the complete `rusty_engine` facade — one Cargo path dependency on the adjacent
  `../rusty-engine` checkout — including `rusty_engine::gameplay_mechanics` (stats, damage and
  restoration, inventory), `rusty_engine::gameplay_resolution` (attempt boundaries, e.g. the
  Doom hitscan path), and `rusty_engine::gameplay_rules` (authored-package admission). Engine
  vocabulary is never re-implemented in parallel; game vocabulary (Doom weapons, doors, hostile
  meanings, death consequences) stays downstream.
- **TypeScript authoring with Rust as the only evaluator.** Gameplay definitions are authored in
  `gameplay/authoring/` (a small grammar + item catalogs behind one import surface), materialized
  deterministically into committed gameplay-rules packages under `data/gameplay/`, and admitted
  by the downstream semantic compiler (`gameplay/src/{authored,compile}.rs`). TypeScript composes
  definitions; it never evaluates gameplay. `pnpm gameplay:check` drift-gates the committed
  artifact and `gameplay-package-check` proves parity with project admission.
- **Content as canonical data.** The E1M1 project is a committed, Studio-owned canonical
  document (`content/projects/doom-e1m1.project.json`) regenerated byte-identically from its
  authoring sources on every verify; `loading-bay`, `relay-annex`, and `converted-wall` are
  additional admitted arrangements of the same meanings.
- **An Engine-owned renderer.** The browser shell and native product render through the
  Engine-hosted application surface (`@rusty-engine/application-host` and the Rust webview
  adapter). The demo owns no canvas, backend, frame decoder, or render loop.

## Run and verify

Install the JavaScript toolchain, build the shell, and launch the Rust host:

```bash
pnpm install --frozen-lockfile
pnpm run build:shell
cargo run --locked -p loading-bay-game --bin browser-host
```

Then open `http://127.0.0.1:8787`. The default project is
`content/projects/loading-bay.project.json`; pass `--project <path>` to select another admitted
project (the E1M1 project keeps the E1M1 card enabled on the menu). Canonical project files are
Studio-owned artifacts; ordinary fixture generation never rewrites them.

The directly rendered Rust-native product and its proofs:

```bash
pnpm run native:doom      # interactive E1M1; WASD moves, arrow keys look
pnpm run verify:native    # native-host + E1M1 machine-checked proof with screenshot capture
```

The desktop (Tauri) shell uses the same Angular build and Rust host; its build, package layout,
and verification are documented in [docs/tauri-desktop.md](docs/tauri-desktop.md):

```bash
pnpm run verify:tauri     # manual workflow: native binary, real WebKit smoke, process lifecycle
pnpm run build:tauri      # deb + AppImage on the documented Ubuntu baseline
```

For a managed LAN-facing session, use the repository manifest:

```bash
den-serve up rusty-engine-demo -repo /absolute/path/to/rusty-engine-demo
```

The launcher builds the browser shell, starts the Rust host on the broker-selected LAN bind and
port, and reports the local and LAN URLs. The managed launch defaults to
`content/projects/doom-e1m1.project.json`. Set `RUSTY_ENGINE_DEMO_PROJECT` to another project
path before `den-serve up` when needed. The process group remains owned by `den-serve`; use its
`status`, `logs`, and `stop` commands with the same project and repository arguments.

The complete product gate is:

```bash
pnpm run verify
```

It typechecks the workspace, drift-checks the authored gameplay package against the committed
canonical artifact, regenerates the canonical projects byte-identically, runs the TypeScript
unit tests, builds the browser shell, and runs the Rust gate (format check, gameplay-package
parity, focused suites, Clippy). Boundary auditing, the native proof, the E1M1 pixel smoke, and
desktop verification are explicit on-demand commands — see
[docs/ci-smoke-inventory.md](docs/ci-smoke-inventory.md).
For Rust-only iteration, `./scripts/verify-rust.sh` remains available.

For focused diagnosis:

```bash
pnpm run check:content       # generated fixtures match; canonical projects Rust-admit and round-trip
pnpm run test:shell          # protocol, projection, input, and presentation units
pnpm run smoke:e1m1          # menu selection, Engine mount, Rust content, and visible canvas pixels
pnpm run certify:e1m1        # explicit full switch/combat/traversal/exit certification
pnpm run audit:boundary      # adjacent facades and forbidden downstream shortcuts
```

`GET /health` identifies a running browser host and `GET /api/state` is a read-only diagnostic
snapshot. Live gameplay commands use the bounded `/api/session` WebSocket; do not debug by adding
HTTP gameplay mutators. `pnpm run generate:content` updates only deliberate fixtures under
`content/generated`; use the Studio/adapter save path for canonical project edits.

The project-owned Studio adapter can be run as a bounded JSON-lines process:

```bash
cargo run --locked -p loading-bay-game --bin studio-adapter
```

It opens only an explicit absolute project root and safe relative project file supplied through
the closed protocol. It exposes Engine-owned catalog, scene, entity, persistence, voxel
inspection, and renderer projection readouts while the game retains its schema and
domain-operation meaning. See [docs/studio-adapter.md](docs/studio-adapter.md).

## Architecture boundary

- Rust owns live gameplay state, substantial logic, explicit scheduling, typed consequences, and
  persistence. The `gameplay/` crate owns game semantics; the shell crate owns hosts, transport,
  persistence glue, and the Studio adapter.
- TypeScript composes immutable content and gameplay definitions and hosts input/presentation;
  canonical game scenes remain serialized Studio-owned projects and TypeScript never becomes a
  second gameplay runtime or evaluator.
- Game-specific presentation code maps typed Rust facts into shared render descriptors. It does
  not own a second renderer, resource cache, effect simulation, or cleanup runtime.
- Dependency direction is `rusty-engine-demo -> rusty-engine` only, through the one facade path
  dependency; Engine owner namespaces stay explicit (`rusty_engine::<owner>`).
- New game semantics belong here first. Do not add a generic Engine hook merely to make a demo
  feature fit.
